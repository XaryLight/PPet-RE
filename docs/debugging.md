# 调试与日志

← [返回 README](../README.md) · [文档索引](README.md)

「模型没显示出来」时，桌宠的透明无边框窗口本身是完全看不见的，很难判断是没加载、
贴图丢了、还是 GL 出错。本项目提供两个互补的调试手段：

| 手段 | 入口 | 适合 |
| --- | --- | --- |
| **模型诊断面板** | 托盘「模型诊断」/ `Ctrl+Shift+D` | 实时查看模型 ID、骨架、图片、渲染帧与是否正常渲染 |
| **失败原因弹窗** | 导入 / 切换 / 重载模型失败时自动弹出 | 立刻看到失败分类、逐条明细与「怎么办」 |
| **结构化日志** | `./last.log`、`Ctrl+D` 快照 | 追溯启动/加载过程、跨线程时序、性能台阶 |
| **渲染验证 CLI** | `ppet_render_verify` | 无人值守判定「模型有没有真的画出来」，见 [Windows 验收](windows-test.md) |

---

## 模型诊断面板

一个独立的 Qt 6 窗口，与主循环共用同一条线程（每帧由 `App` 驱动 Qt 事件分发），
不额外开线程、不创建第二个 GL 上下文。面板可见时每 **200 ms** 自动刷新，
不可见时零开销。

### 六个标签页

| 标签页 | 内容 |
| --- | --- |
| **概览与渲染** | 状态灯、**模型 ID**（路径 + 类型哈希，便于对照日志）、模型名 / 类型 / 路径 / **来源压缩包**、加载状态、渲染结论；**实际出图 Pixels**（帧缓冲读回的非透明像素占比，最可信的一行）、GPU 就绪、GL 错误、Draw calls、贴图「引用/已加载/缺失」、FPS、帧时、帧数、视口、渲染缩放、桌面尺寸、全屏追踪状态、全局与局部光标 |
| **参数** | 顶点数、索引数、三角形数、骨骼数、材质数、子网格数、Morph/表情数、贴图引用/已加载/缺失数、包围盒、模型高度、是否蒙皮、双面材质、描边 |
| **骨架信息** | 逐根骨骼一行：**ID、名称、父骨骼、层级深度、属性**（可位移 / IK / 根骨骼）。顶部汇总骨骼总数与最大层级。数据由 `FillMeshDebugInfo()` 从 `SkinnedMesh::bones` 统一生成，PMX / VRM 都能看 |
| **图片渲染** | 上半部是**贴图缩略图**（PMX / Live2D 的磁盘贴图用 `QPixmap` 直接预览，VRM 内嵌贴图列条目与解码状态）；下半部是**当前渲染帧实时预览** —— 面板可见时每 200 ms 用 `glReadPixels` 抓一帧 PNG，可直观看模型有没有画出来、位置对不对 |
| **模型部分** | 每个子网格/材质一行：名称、三角形数、材质索引、详情（贴图索引 / 双面 / 描边）。对应 `SkinnedMesh::subMeshes` |
| **性质与资源** | 格式版本、文本编码、坐标系转换、渲染管线、控制骨骼命中情况等「性质」；**错误与警告（详细）**：分类、结论、逐条明细、缺失资源；**缺失资源清单**（具体路径）；日志文件位置 |

> 抓帧只在面板可见且到达刷新时刻才执行，关闭面板后零开销。
> Live2D 是二维部件管线，本来没有骨骼，「骨架信息」页为空属正常。

### 状态灯

| 颜色 | 含义 | 判定条件 |
| --- | --- | --- |
| 🟢 绿 | 正常渲染 | 已加载 + GPU 就绪 + 网格非空 + 无 GL 错误 + 无缺失贴图 + **帧缓冲有非透明像素** |
| 🟡 黄 | 可渲染，但存在问题 | 有缺失贴图，或贴图已加载数 < 引用数（**很可能白模**） |
| 🔴 红 | 渲染异常 | 未通过综合判定、检测到 GL 错误，或**帧缓冲 0 个非透明像素（没出图）** |
| ⚪ 灰 | 尚未加载模型 | — |

「渲染结论」是一句可读文字，例如 `可出图，但缺 3 张贴图（可能白模）`、`网格为空，无法渲染`、
`GL 错误码 1282`、`帧缓冲为空：模型未出图（0% 覆盖率）`、`正常渲染`。

> **为什么必须看「实际出图 Pixels」**：模型后端的 `renderingOk` 只检查
> 网格非空、GPU 资源就绪、GL 错误为 0，加上 draw calls、贴图、FPS 全是间接指标 ——
> 主循环若漏了每帧清屏，这些数字照样全绿，帧缓冲却一个像素都没有，屏幕上什么都看不到。
> 面板因此会在「渲染状态」第一行显示读回的**非透明像素覆盖率**：为 `0.00% ← 未出图`
> 时状态灯直接转红，结论写明原因与排查方向。不打开面板时，主循环每 120 帧
> 也会做一次轻量读回，异常时往 `last.log` 记一条 `RENDER` 错误。

### 复制诊断摘要

右下角「复制诊断摘要」把当前快照拼成纯文本写进剪贴板，可直接粘到 GitHub Issue。
包含模型信息、规模参数、贴图命中、FPS、性质与缺失资源清单。

> 数据来源：模型部分由 `IModel::DebugInfo()` 提供（PMX / VRM / Live2D 各自填充，
> 新增后端不实现时只显示概览，面板不会崩）；运行时数据由 `App` 每帧采集成 `RuntimeStats`。
> GL 错误通过 `ConsumeGlErrors()` 消费错误队列得到。

## 添加模型失败弹窗

从托盘「导入模型」、设置面板选模型、切换模型或「重新渲染」时，如果加载失败（或成功但有隐患），
会弹出一个独立的 Qt 窗口，把原因分层说明，而不是只往日志里丢一句 `加载失败`：

| 区域 | 内容 |
| --- | --- |
| 标题 / 状态灯 | 红色「模型加载失败」或黄色「模型加载警告」（非硬失败） |
| 分类 | 例如 `未找到有效骨架`、`模型图片缺失`、`解析错误`、`moc3 模型错误`、`模型包错误`、`后端未启用` |
| 摘要 / 文件 | 一句话原因与涉及的文件或压缩包路径 |
| **详细信息** | 逐条编号的明细：缺了哪几张贴图、解析停在哪一步、模型类型与解析入口；以及分类对应的**可操作建议** |
| 日志 | `last.log` 路径，可一键「复制详情」贴到 issue |

分类由 `src/tools/model/ModelError.hpp` 定义（10 类），
后端返回的错误串会经 `InferErrorCategory()` 自动归类；调用方在阶段明确时（如 ZIP 解压失败）直接指定分类。

**两类最容易被误判为「没反应」的情况会弹黄色警告**（模型其实加载成功了）：

- **未找到有效骨架**：PMX/VRM 解析后骨骼数为 0，无法做蒙皮动画与视线追踪；
- **模型图片缺失**：PMX 单文件导入时贴图路径指向不存在的文件 → 白模。
  建议里会明确「把 `.pmx` 与 `tex/` 一起打包成 `.zip` 再导入」。

> 启动时的自动加载**不弹窗**（避免每次开机打扰），失败信息仍写 `last.log`，
> 并可在诊断面板「性质与资源 → 错误与警告（详细）」里查看。

## 结构化日志

程序运行时的所有调试信息都会写入当前工作目录下的 **`./last.log`**（UTF-8 编码，带 BOM），
用任意编辑器打开即可看到正常中文，不会出现「灏氭湭鍔犺浇妯″瀷」这类乱码。

### 一行长什么样

```
2026-11-07 12:34:56.789 | +0000123.456 | Δ   0.123 | INFO  | a3f1 | [MODEL] App.cpp:280 App::LoadModel | 模型加载成功：初音ミク（PMX / PMX 2.0 / 12.3 ms）
└──────── 墙钟（毫秒）──┘ └─ 进程相对 ─┘ └ 距上条 ┘ └级别┘ └线程┘ └──────── 模块 / 源码位置 ────────┘ └ 消息
```

字段用 ` | ` 分隔，**严格单行**，可机器解析：

| 字段 | 说明 |
| --- | --- |
| 墙钟时间 | `YYYY-MM-DD HH:MM:SS.mmm`，精确到毫秒（旧版只有 `HH:MM:SS`，无法定位先后顺序与卡顿） |
| 进程相对毫秒 | `+0000123.456`，自进程启动以来的毫秒数 |
| Δ 毫秒 | 距**上一条**日志的间隔，直接看出耗时台阶（例如解压、纹理解码造成的停顿） |
| 级别 | `TRACE` / `DEBUG` / `INFO ` / `WARN ` / `ERROR` / `FATAL`，定宽 5 字符 |
| 线程 ID | `std::thread::id` 的短哈希，Linux 托盘线程与主线程交错输出时能立刻区分 |
| 模块 / 源码位置 | `[自动标签或显式 tag] 文件:行号 函数`，由 `std::source_location` 自动生成 |
| 消息 | 尾部换行自动去掉，内部换行转义成 `\n`、制表符展开为空格 |

自动标签从源码文件名推导（`PmxModel.cpp` → `[PmxModel]`），
也可用 `PPET_LOG_TAG("PMX", ...)` 显式指定（项目里 `[PKG]` 模型包、`[MODEL]` 模型加载、
`[DEBUG]` 调试快照）。

### 日志级别与开关

| 级别 | 用途 |
| --- | --- |
| `TRACE` | 最细：逐条目、逐帧状态 |
| `DEBUG` | 关键分支、参数快照（**文件默认阈值**） |
| `INFO` | 启动、加载、用户动作（**控制台默认阈值**） |
| `WARN` | 可继续但数据/环境异常 |
| `ERROR` | 功能失败 |
| `FATAL` | 致命（不主动 abort，由调用方决定退出） |
| `OFF` | 全部关闭 |

两种调整方式，命令行优先于环境变量：

```bash
# 环境变量
PPET_LOG_LEVEL=trace PPET_LOG_CONSOLE_LEVEL=debug ./build/bin/ppet

# 命令行
./build/bin/ppet --log-level=trace --log-console-level=debug
```

| 变量 / 参数 | 默认 | 作用 |
| --- | --- | --- |
| `PPET_LOG_LEVEL` / `--log-level=` | `debug` | 文件与总体阈值，低于它的日志连字符串都不格式化 |
| `PPET_LOG_CONSOLE_LEVEL` / `--log-console-level=` | `info` | 控制台阈值，避免 TRACE/DEBUG 刷屏 |

> 文件与控制台是**双阈值**：把控制台保持 `info`、文件开到 `trace`，
> 既不被刷屏，又能在事后拿到完整现场。

### 文件行为

- 默认 `./last.log`；工作目录只读时自动回退到系统临时目录 `ppet-last.log`
  （启动时日志会打印实际路径）。
- UTF-8 + BOM，追加写入，每行立即 `fflush`，崩溃也不会丢最后几条。
- 超过 **4 MiB** 时轮转成 `last.log.1` 并重新写 BOM，避免无限膨胀。
- 全量写出由 `std::mutex` 保护，多线程不会把两行搅在一起。

## 典型排查流程

1. **程序启动了但什么都没有** → 打开「模型诊断」，看「尚未加载模型」还是「网格为空」；
   同时确认 `last.log` 里有没有 `模型加载失败`。
2. **模型是白模 / 纯色** → 诊断面板「性质与资源」页看缺失资源清单；
   日志里会有 `模型引用了 N 个不存在的资源文件` 与 PMX 打包建议。
   按 [模型格式与导入](models.md#pmx-请用-zip-导入重要) 重新打包 `.zip`。
3. **帧率低 / 卡顿** → 看日志的 `Δ` 列定位耗时台阶，诊断面板看 FPS、帧时与 Draw calls。
4. **Windows 双击闪退** → 看 [构建指南 · Windows 常见故障排查](build.md#windows-常见故障排查)。
5. **中文乱码** → 直接看 `./last.log`（UTF-8）；控制台乱码是终端按 GBK 解释了 UTF-8 字节，
   `main.cpp` 已调用 `SetConsoleOutputCP(CP_UTF8)`，仍未生效时以文件为准。

### 常见问题速查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `resume request failed - process already running` | CLion 残留进程 | 结束旧进程后再运行 |
| 退出码 `3221225781 (0xC0000135)` | `STATUS_DLL_NOT_FOUND` | 缺 `Live2DCubismCore.dll` / MinGW 运行时 DLL / Qt DLL，见 [构建指南](build.md#运行时-dll-部署) |
| `ld.lld: could not open 'libLIBCMT.a'` | 链接了 MSVC 静态库 | MinGW 必须用 DLL 导入库，见 [构建指南](build.md#windows-工具链选择重要) |
| 日志无输出 | 级别被调到 `off`，或工作目录不可写 | 去掉 `--log-level=off`；看启动日志里的实际日志路径 |
| `last.log` 里两行搅在一起 | 不会发生（已加锁）；若出现请提 issue | — |
